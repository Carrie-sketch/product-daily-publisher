# 任务资料

这些是已经跑通过的发文规则，和具体产品无关。不要重新设计流程，不要改接口路径，不要缩短等待时间。使用者只补充自己的产品资料、关键词和密钥。

## 这个技能提供什么

别人自己做，容易在这些地方返工：

- 同一天连发被平台删文或改成非公开
- CodeLegion 连发触发限流后删帖
- 先发了副站、canonical 指错
- 日语平台没有文章发布接口，却去猜一个接口
- 定时任务在个人电脑上，关机后不再跑
- 失败后重跑，把已经发出的文章又发一遍
- 钉钉字段 ID 没先读取，直接用错列名导致回填失败
- 模型密钥和平台密钥分成两个文件，发文进程只加载了其中一个，日语稿发不出去
- 文末没有引流链接，或者链接是猜出来的

本技能把这些约束写死。AI 负责按约束接入使用者自己的产品，而不是再发明一套发文系统。

## 每天的固定节奏

服务器本地时间 10:00 启动。当天已成功则跳过。10:00 没完成，当天每 30 分钟再试，直到 21:30。已经写出成功标记后，后续触发必须直接退出。

一天处理 2 个关键词。每个关键词的英文槽位顺序不能变：

1. 主 dev.to
2. 副 dev.to
3. 主 CodeLegion，canonical 必须是主 dev.to 的公开链接
4. 副 CodeLegion，canonical 必须是副 dev.to 的公开链接，发之前至少等 30 秒

两个关键词之间至少等 60 秒。不要并发发帖。

Zenn 和 Qiita 是可选日语平台。每个账号每个平台每天只发 1 篇，挂在当天第一个成功的关键词后面。第二个关键词不再发这两个平台。默认关闭，使用者确认后才开启。

英文槽位有一个失败，就停止这个关键词的后续槽位，避免留下没有来源链接的文章。日语平台失败不删除、不撤回已经发出的英文文章，只记录失败，并允许当天稍后只补日语平台。

## 平台接法

dev.to：

- 接口：`POST https://dev.to/api/articles`
- 请求头：`api-key`
- 正文放在 `article.body_markdown`，`published` 为 true
- 标签最多 4 个，只保留字母和数字，每个最长 20 个字符
- 发之前用 `GET https://dev.to/api/users/me` 核对账号，对不上就停止

CodeLegion：

- 接口：`POST https://coderlegion.com/api/v1/posts`
- 请求头：`X-API-Key` 和 `User-Id`。`User-Id` 是数字用户 ID，不是 Bearer
- 分类用使用者配置的 `CODELEGION_CATEGORY_ID`。未配置时不要猜测，先问
- 必须带 `canonical_url`，指向对应的 dev.to 文章
- 公开链接用 `https://coderlegion.com/{id}`。不要使用 `/posts/{id}`，那个路径会 404
- 同一账号连续发帖会触发限流甚至删帖。两篇之间至少 30 秒，两个关键词之间至少 60 秒

Qiita：

- 接口：`POST https://qiita.com/api/v2/items`
- 请求头：`Authorization: Bearer <令牌>`
- 先用 `GET /api/v2/authenticated_user` 核对用户名
- 正文用 Markdown。`private` 为 false，`tweet` 为 false
- 标签 1 到 5 个，每项是 `{"name": "标签名", "versions": []}`
- 返回 429 时按 5 分钟、10 分钟、15 分钟等待后再试，最多 3 次。不要立刻重打
- 平台把文章改成非公开时，不要原样重发

Zenn：

- 没有可用的文章发布接口。不要猜测 `POST /api/articles` 之类的地址
- 使用者自己建空的 GitHub 仓库，在 Zenn 后台只关联这一个仓库，同步分支一般是 `main`
- 文章放在仓库的 `articles/{slug}.md`
- slug 只能是小写字母、数字、连字符和下划线，长度 12 到 50
- 文件开头必须有 front matter：`title`、`emoji`、`type: tech`、`topics`、`published: true`
- 推送到关联分支后，由 Zenn 同步。公开地址是 `https://zenn.dev/{用户名}/articles/{slug}`
- 服务器访问 GitHub 的 443 不通时，用仓库部署密钥走 SSH。不要改用一个不存在的 HTTP 接口
- 从 Git 删除文件不会删除 Zenn 上的文章。已下架的文章不要再推回去

Medium 不自动发。使用者从 dev.to 导入后，自行把链接填进 `Medium链接`。

## 写文章

遵守 `references/writing-rules.md`。

补充这些已经验证过的要求：

- 同一关键词的 4 个英文槽位要是 4 篇不同角度的文章，不能只改标题后复用同一篇正文
- 日语平台的两篇也不能互译。Qiita 用排查清单角度，Zenn 用操作步骤角度
- 模型调用必须同时读到平台密钥和模型密钥。只加载 `keys.env` 会导致日语稿在调用模型前失败
- 主模型超时或过载时，切换到使用者配置的备用模型。不要无限重试同一个失败模型
- 生成结果太短、没有要求的语言，或包含配置里禁止的说法时，视为失败，不发这一篇

## 记录表

表头以 `references/steps.md` 第 8 步为准，名称不能改。

回填规则：

- 用关键词找到唯一一行。找不到，或找到多行，就停止写入
- 只更新这一行的链接、状态和发布日期
- 用字段 ID 提交更新。平台列名曾经被表格改过一次后，按显示名更新会整批失败
- 有槽位没发出时，不要把状态改成已发布，也不要清空已有链接

## 服务器定时任务

必须放在常开的服务器上。个人电脑和当前对话都不能当作每天自动发文的运行环境。

定时任务要满足：

- 时区是使用者确认的本地时间
- 10:00 到 21:30，每 30 分钟触发一次
- 进程内若发现今天已经成功，立即退出
- PATH 包含 python、dws 和模型命令的真实目录
- 标准输出和错误写入 `state/cron.log`，日志里不能出现密钥
- 用文件锁防止两次触发叠在一起
- 生成失败可以整天重试。部分文章已经发出后，不能把整个关键词重发，只能补未完成的平台

## 失败后怎么处理

| 现象 | 处理 |
| --- | --- |
| 平台返回 429 | 按该平台的等待时间后退，不要连打 |
| 英文槽位失败 | 停止该关键词后续槽位 |
| 日语平台失败 | 保留英文文章，当天只补日语平台 |
| 账号核对失败 | 停止，不发文 |
| 文章被平台下架或改成非公开 | 不原样重发，先告诉使用者 |
| 钉钉回填失败 | 文章链接已经打印到日志时，不要为了回填而重发文章 |
| 模型超时 | 切换备用模型；备用模型也失败则当天稍后重试，不发空文 |

告警渠道由使用者自己配置。没有配置告警时，失败必须写进当天日志，并在下一次汇报里说明。不要把告警发到别人的账号。
